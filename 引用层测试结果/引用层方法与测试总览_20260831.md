# 引用层方法与测试总览

## 一句话结论

当前程序已经实现回答层内部的引用约束模块：检索证据先被规范化为稳定的 `E001`、`E002` 编号，经过预算和相关性筛选后，回答模型只能为结构化事实主张绑定这些证据编号；程序再检查未知编号、漏引、仅引用背景证据和模型手写引用标记。校验失败只允许修复一次，仍失败则安全停止，不展示未经验证的模型草稿。

“引用层”在架构上是**回答层内部的可替换子模块**，不是与输入层、索引层、检索层、回答层平级的新层。

## 引用层内部流程

```mermaid
flowchart TD
    EVIDENCE["检索证据块<br/>record_id + provenance + source_block_ids"] --> IDS["EvidenceNormalizer<br/>去重、排序、分配 E001…"]
    IDS --> FILTER["EvidenceSelector<br/>只保留 relevant 证据"]
    FILTER --> DIRECT{"是否至少有 direct / conflict？"}
    DIRECT -->|否| RECHECK["支持性复核<br/>必要时要求逐字 support_quote"]
    RECHECK --> DIRECT2{"复核后有 direct / conflict？"}
    DIRECT2 -->|否| INSUFFICIENT["insufficient_evidence<br/>生成前拒答"]
    DIRECT2 -->|是| DRAFT
    DIRECT -->|是| DRAFT["LLMAnswerGenerator<br/>answerable + claims + evidence_ids"]
    DRAFT --> VALIDATE{"CitationValidator"}
    VALIDATE --> CHECK1["claim 至少一个引用"]
    VALIDATE --> CHECK2["引用 ID 必须存在"]
    VALIDATE --> CHECK3["至少包含 direct/conflict"]
    VALIDATE --> CHECK4["claim.text 禁止手写 [E001]"]
    CHECK1 --> RESULT{"全部通过？"}
    CHECK2 --> RESULT
    CHECK3 --> RESULT
    CHECK4 --> RESULT
    RESULT -->|是| APP["AnswerRenderer<br/>由应用追加引用标记"]
    RESULT -->|否，首次| REPAIR["把错误和旧结构交给模型<br/>只修复结构"]
    REPAIR --> VALIDATE2["第二次校验"]
    VALIDATE2 -->|通过| APP
    VALIDATE2 -->|失败| CLOSED["安全失败<br/>不返回模型草稿"]
```

## 解耦情况

| 插槽 | 当前实现 | 可替换项 | 需要保持的契约 |
|---|---|---|---|
| 证据编号 | `EvidenceNormalizer` | 其他去重、排序、编号策略 | 输出唯一 `EvidenceItem.evidence_id` |
| 证据筛选 | `LLMEvidenceSelector` + Ollama | 规则、reranker、其他模型 | 输出 `EvidenceDecision` |
| 主张生成 | `LLMAnswerGenerator` + Ollama | 其他结构化生成器 | 输出 `AnswerDraft` 与 `AnswerClaim` |
| 引用校验 | `CitationValidator` | 更严格的蕴含校验器 | 返回错误列表，不直接改写答案 |
| 引用渲染 | `AnswerRenderer` | Markdown、HTML、脚注格式 | 只使用已经校验的证据 ID |
| 引用来源 | `Citation.from_evidence` | API 或数据库引用对象 | 保留 record、文件、坐标、block ID |

## 当前最重要的边界

1. 引用编号由程序分配，模型不能创造编号。
2. 最终 `[E001]` 由应用渲染，不直接信任模型手写文本。
3. 每条主张至少需要一条被筛选器判为 `direct` 或 `conflict` 的证据。
4. 当前校验器验证的是引用结构、ID 合法性和支持等级，不执行逐句自然语言蕴含判断。
5. 因此“引用校验通过”表示答案受到有效证据约束，不等同于已经数学证明每个词都被证据蕴含。
