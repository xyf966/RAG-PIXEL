# 索引层当前方法

## 1. 索引层的输入与边界

索引层不重新解析 Word、PPT、Excel 或 PDF。它只接收输入层输出的 `HybridDocument schema 1.1`：

- `kind=text`：正文、标题、列表等语义文字；
- `kind=table`：表格正文、原生 cells、合并范围、公式和来源位置；
- `kind=visual`：图片、图表、图标、示意图等视觉对象及其页码、bbox 和原生 locator；
- `vision_results`：识别阶段保持为空，避免 Pixel 与输入解析耦合。

schema 2.0 构建会拒绝其他版本的 `HybridDocument`。旧的 `hybrid-index.json / semantic-index.json / image-index.faiss` 属于 schema 1.x，不能直接迁移，必须重新构建。

## 2. 文字索引方法

文字按 `reading_order` 排序，并识别标题层级。分块不会跨越不同页面、幻灯片或工作表，也不会跨越标题路径。

默认参数：

| 参数 | 当前值 | 作用 |
|---|---:|---|
| `text_target_tokens` | 512 | 达到目标长度后优先结束当前块 |
| `text_max_tokens` | 768 | 任何 embedding 文本都不能超过的硬上限 |
| `text_overlap_tokens` | 96 | 相邻块保留的上下文重叠 |
| `text_batch_size` | 8 | 文本向量化批量大小 |

每个文字记录保留：

- 标题路径 `title_path`；
- 所有来源块 `source_block_ids`；
- 重叠来源 `overlap_source_block_ids`；
- 每个来源块的完整 `provenance`；
- 原始正文与实际送入模型的 `embedding_text`；
- 基于文档、模态、来源块、序号和内容哈希生成的稳定 `record_id`。

超长内容先按句号、问号、分号和换行拆分；仍超长时才使用带重叠的硬窗口。

## 3. 表格索引方法

表格不会被当成普通长文本直接切断。程序按以下优先级恢复矩阵：

1. Excel/openpyxl 的原生 `cells`；
2. 文档解析器的 `table_cells`；
3. Markdown 表格；
4. 无法结构化时才使用显式 `raw` 后备。

标准化时保留：

- 表头、数据行和检测到的标题行；
- 原生单元格与结构化单元格；
- 合并范围、行列跨度和公式；
- 原始表格正文；
- 工作表、单元格范围、页码或幻灯片位置。

默认每个表格块最多 20 行、12 列。宽表拆分时始终重复第一列；长表拆分时始终重复表头。单个超长单元格仍会受 768 token 硬上限约束，并使用重叠窗口继续拆分。

送入模型的文本形式类似：

```text
Table: 表格标题
Columns: 列1 | 列2 | 列3
Row: 值1 | 值2 | 值3
Source: Sheet1!A1:C20
```

原始内容和结构矩阵保存在 metadata 中，因此未来检索命中后仍能回到真实单元格，而不是只剩一段扁平文本。

## 4. 视觉索引方法

视觉入口只接受 `kind=visual` 且 `metadata.indexable != false` 的对象。程序会检查：

- `block_id` 不能为空且全局唯一；
- `visual_type` 必须属于支持集合；
- 非视觉块不能进入视觉物化流程；
- 背景页等 `indexable=false` 对象直接跳过。

### 4.1 Office

默认策略为 `office_visual_policy=require-com`。Word、PowerPoint、Excel 必须通过 Microsoft Office COM 导出可见对象：

- Word：`CopyAsPicture`；
- PowerPoint：`Shape.Export`；
- Excel：`Chart.Export` 或 `Shape.CopyPicture`。

策略可选值：

| 策略 | 含义 |
|---|---|
| `require-com` | 必须成功调用 COM；允许对象导出后按规则继续处理 |
| `require-native` | 每个对象都必须得到认可的原生导出结果，缺失一个就失败 |
| `allow-page-fallback` | 原生导出失败时允许按已识别 page+bbox 裁切页面区域 |

正式 Office 视觉索引要求严格策略。`current_snapshot()` 会拒绝未使用 `require-com` 或 `require-native` 构建的 Office visual 快照。

### 4.2 PDF

PDF 视觉对象在识别阶段不截图。索引阶段才根据 `page + bbox` 以 2 倍矩阵裁切目标区域：

- bbox 为 0～1 时按页面宽高还原；
- bbox 为点坐标时直接使用；
- 页码、bbox 缺失或区域为空时记录过滤原因；
- 正文和表格不会因为 PDF 裁图而进入 Pixel。

### 4.3 图片质量门与去重

物化图片进入 Pillow 质量门：

- 透明图片合成白底；
- 过滤尺寸异常、纯白、纯黑和占位图片；
- 计算内容 SHA-256；
- 同一 SHA-256 的图片只计算一次 embedding；
- 重复对象仍各自保留 `IndexRecord`，并记录 `embedding_duplicate_of`。

Pixel 首次漏回向量时自动重试一次；仍无向量、零向量、非有限值或维度错误会使构建失败。

## 5. 向量模型

当前三种模态统一使用 Qwen3-VL-Embedding-2B：

- 文字：模型文本接口 + 文字检索指令；
- 表格：模型文本接口 + 表格检索指令；
- 视觉：PixelRAG 图像接口；
- 维度：2048；
- 归一化：L2；
- FAISS：`IndexFlatIP`，归一化后内积等价于余弦相似度。

同一次构建共用一个常驻 `PixelRAGEmbeddingSession`，模型只加载一次，完成后统一释放。

## 6. 快照构建与发布

构建过程先写入 `.staging-<build-id>`：

1. 生成文字和表格记录；
2. 物化视觉对象并生成三类向量；
3. 写入三个 FAISS 和三个 metadata JSONL；
4. 校验数量、维度、范数、来源、路径和哈希；
5. 写入 `build-report.json` 与 `manifest.json`；
6. 将 staging 原子移动为 `snapshots/<build-id>`；
7. 最后原子更新 `CURRENT`。

任一步失败都会删除 staging，并保留原 `CURRENT` 指向的快照。

## 7. 当前没有做什么

以下功能尚未接入 schema 2.0：

- 查询文本/图片编码；
- text、table、visual 三路召回；
- 不同模态分数归一化与融合；
- 坐标证据回链和上下文组装；
- LLM 最终回答。

因此当前测试结论只覆盖“索引构建正确”，不覆盖“检索效果好”。
